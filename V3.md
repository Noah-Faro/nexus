# NEXUS V3 Master Blueprint

This document represents the ultimate architectural and feature roadmap for the NEXUS Super-App. It systematically merges the **V2 Training Roadmap**, **Project Athena (Local LLM)**, and the advanced ML and Data concepts detailed in **IDEAS.md** and **IDEASVERBOSE.md**. 

> [!WARNING]
> **Expo Architecture Requirement**
> Because `react-native-health`, `react-native-coreml` (or similar native ML modules), `react-native-quick-crypto`, and `react-native-llama` require Native Modules, the project must transition completely to **Expo Development Builds** (Custom Dev Client) via `expo prebuild`. Standard Expo Go will not work.

## Phase 6: Data Sourcing, HealthKit Aggregation & DB Re-architecture

Before introducing advanced ML or LLM capabilities, the foundational data storage and sourcing layer must be completely overhauled to support large tensors and high-frequency time-series data without crashing the device or the AES Vault.

### 6.1. Mobile-First Health Aggregation
- **HealthKit as the Data Lake:** Integrate `react-native-health` (iOS) or `react-native-health-connect` (Android). Instead of building custom sync pipelines for Oura, Whoop, and MyFitnessPal, NEXUS will read directly from the OS health stores where these wearables natively sync.
- **Background Limitations & Aggregation:** HealthKit data is hardware-encrypted and inaccessible when the device is locked. Thus, data pulling will happen aggressively upon **App Foreground/Launch**. 
- **Vault Safety:** Raw time-series data (e.g., minute-by-minute heart rate) will **never** be injected into the AES Drive Vault. It will be compressed locally into daily summary objects (e.g., `DailyRecoverySummary`) before encryption to prevent massive JSON merge conflicts and Google Drive API rate limits.

### 6.2. The "Index + Blob" ML Storage Architecture
- **Deprecating AsyncStorage for Tensors:** Relying on `AsyncStorage` and JS-based `crypto-js` for massive ML matrices will cause out-of-memory (OOM) crashes and freeze the UI thread.
- **Binary Blobs:** Use SQLite strictly as a fast indexer (metadata, timestamps). Store raw tensors as immutable binary files (e.g., `.bin` or Protocol Buffers) directly on the local file system.
- **Native Cryptography:** Implement JSI-based native crypto (`react-native-quick-crypto`) to encrypt these binary files completely off the JS thread.
- **Chunked Cloud Sync:** Abandon per-row CRDT tracking for ML data. Upload the encrypted tensors as immutable time-window chunks (e.g., `tensor_2026-05-31.enc`) to Google Drive.

## Phase 7: Lifestyle Pillars (Sleep, Recovery, Habits & Nutrition)

Implementation of the remaining core lifestyle tracking modules, designed to feed high-quality holistic data into the ML engines.

### 7.1. Sleep & Recovery Module
- **Subjective Morning Check-In:** A brief daily intake flow capturing subjective fatigue, muscle soreness, and stress levels.
- **Sleep Tracking:** Import sleep duration, sleep stages, resting HR, and HRV from HealthKit.
- **Recovery Composite Score (0-100):** Synthesize the check-in data and HealthKit data into a single daily readiness metric.

### 7.2. Protocol / Habit Engine
- **Synthesized Protocols:** Group habits into stacks (e.g., "Morning Huberman Routine").
- **Dynamic Triggers:** Create rules-based activation (e.g., trigger post-workout protocol automatically after a training session).
- **Streak Tracking:** Visual adherence heatmaps mapping closely with the user's mood and recovery.

### 7.3. Nutrition & Macro Tracking
- **Quick Logging:** Quick entry for Protein, Carbs, Fats, and Calories. 
- **Barcode Scanning:** Integration for scanning nutritional labels.
- **Hydration Synergy:** Water-dense foods automatically scale the day's hydration progress, and high-caffeine foods feed into the Caffeine clearance timescales.

### 7.4. Cross-Module Insights Dashboard
- **Unified Timeline:** A single chronological UI merging logs from Hydration, Caffeine, Training, and Nutrition.
- **OLED Visualizations:** Implement the interactive "Caffeine/Sleep Curve" visualization. A user can dynamically "add" a simulated coffee to their timeline and watch the predicted sleep onset latency shift into the red zone if it crosses the sleep-safe physiological threshold.

## Phase 8: V2 Deterministic Training Coach

Expanding the existing training module with intelligent periodization and volume management algorithms.

### 8.1. Bayesian Onboarding (Cold Start Prevention)
- Volume tracking algorithms require historical data. Seed the engine with population averages (Bayesian Priors) by capturing Training Age, Body Weight, and Goals during an initial onboarding flow.

### 8.2. Volume Landmarks (MEV/MAV/MRV)
- Track weekly sets per muscle group. 
- Automatically warn the user when approaching MRV (Maximum Recoverable Volume) or if they are dropping below MEV (Minimum Effective Volume).

### 8.3. Periodization Models & Fatigue Management
- Allow users to switch between **Linear Progression**, **Daily Undulating Periodization (DUP)**, and **Block Periodization**. The deterministic engine will calculate session targets based on the selected model.
- **Rolling RPE:** Track average RPE across mesocycles to dynamically suggest deload weeks when systemic fatigue is detected.
- **Predictive 1RM:** Graph estimated 1RM trends to predict milestone lifts.

## Phase 9: Local Machine Learning Engine (CoreML Shift)

A sophisticated on-device ML architecture designed to reverse-engineer subjective wellness targets.

> [!CAUTION]
> **OOM Prevention:** `@tensorflow/tfjs-react-native` incurs immense RAM overhead on iOS. To safely co-exist with the rest of the app, this engine must be built using `react-native-coreml`, leveraging the iPhone 11 Pro's A13 Bionic Neural Engine for massive memory savings.

### 9.1. Ground Truth via Unsupervised Learning
- Instead of relying solely on the user to label their sleep quality, run **Gaussian Mixture Models (GMM) / K-Means clustering** on morning vitals (waking HRV, RHR) to define personalized, discrete physiological "Recovery States" (e.g., Optimal, Neutral, Depleted).

### 9.2. Model Assignment Strategy (Supervised)
- **Sleep Quality & Mood (XGBoost):** XGBoost inherently handles complex, non-linear feature interactions (e.g., caffeine only damages sleep if taken *after* a specific threshold) without requiring aggressive imputation.
- **Required Sleep (Lasso Regression):** A user's sleep need is additive. Lasso's L1 penalty automatically shrinks irrelevant features to zero, maintaining a robust, non-overfit regression curve.
- **Training Readiness (Isolation Forest):** Uniquely sensitive to acute stressors (illness, alcohol). Anomaly detection easily flags "out of bounds" physiological drops.
- **Reverse Engineering:** The ML engine queries the XGBoost model mathematically: *"What is the minimum sleep duration required tonight to achieve a >85% probability of landing in the 'Optimal' recovery cluster tomorrow?"*

## Phase 10: Project Athena (Local LLM Interceptor)

The final layer: deploying an empathetic LLM over the deterministic algorithms to dynamically adjust recommendations based on human context.

### 10.1. Local Model Infrastructure
- **Native Dependency:** Integrate `react-native-llama`. 
- **Model Parameters:** Fetch the ~800MB GGUF Llama-3.2-1B-Instruct model. To fit within the iOS Jetsam limit (~1.5GB total app memory), the model **must** use aggressive `Q3_K_M` or `Q4_K_M` quantization.

### 10.2. Strict Mutual Exclusion Engine
- An iPhone 11 Pro cannot hold CoreML matrices, React Native UI state, and the LLM KV-cache in memory simultaneously.
- Build a lifecycle manager that **explicitly destroys** CoreML instances natively (bypassing JS garbage collection delays) and temporarily unmounts complex React UI views *before* the `llama.cpp` context is instantiated.

### 10.3. Context Aggregation & Interception
- **Payload Construction:** Feed the LLM a highly compressed context string (max 512–1024 tokens) containing the last 14 days of Phase 7 Sleep/Recovery data and the Phase 8 deterministic target.
- **Streaming UI:** Do not use a strict 5-second timeout, as LLM cold-start on the A13 chip will take 1-2 seconds. Instead, implement **streaming generation** directly into the UI's CoachCard. The user watches the LLM "think" in real-time. If Athena agrees with the deterministic target, she streams a concise, contextual affirmation. If she overrides it (e.g., dropping the target RPE due to a poor recovery score), she explicitly explains why.
